# ADR 0008: first WASM backend and Value-handle ABI

Status: accepted — the first WASM backend.

## Purpose

WASM is a derived execution format, not the semantic representation of an image program. The first backend should prove that `lagrange-code/v0` can compile to real WebAssembly and execute through the same Block/activation machinery as the bootstrap interpreter without choosing a lossy object/value layout too early.

## ABI v0

The first ABI is named:

```text
lagrange-value-handle/v0
```

Every language Value visible to WASM is represented by an invocation-local `i32` handle into a host-owned canonical Value arena.

Handle `0` is reserved for the absence of a receiver/ABI value. Positive handles are valid only for the current activation. They are not object IDs, capabilities, addresses, durable references or values that may be persisted in the image.

A compiled entry has the logical signature:

```text
run(receiverHandle,
    argumentHandle0, ...,
    captureHandle0, ...)
  -> resultHandle
```

All physical parameters and the result are WASM `i32` values.

The receiver is first and remains separate from positional arguments. Arguments follow source order. Captures follow the stable binding-ID order recorded by the semantic program/function artifact. The executor resolves captured Values from the Block's LexicalEnvironment immediately before invocation.

This keeps the existing neutral calling convention intact while avoiding an early commitment such as `i64 == SmallInteger`, linear-memory object layouts or WASM references as image identity.

## Host Value arena

`ValueHandleArena` owns canonical tagged Values for one activation. Host imports validate every incoming handle before operating on it.

The first import module is `lagrange` and exposes:

```text
literal(index)                 -> valueHandle
integer_add(left, right)       -> valueHandle
equals(left, right)            -> booleanValueHandle
is_true(booleanValueHandle)    -> i32 0|1
```

`integer_add` uses the existing arbitrary-precision integer Value semantics on the host. WASM therefore does not narrow image integers to 32 or 64 bits in this ABI.

`equals` compares canonical Values. `is_true` is the explicit bridge needed for WASM structured control flow while preserving tagged boolean Values at the semantic boundary.

Literal Values are derived module metadata indexed by the generated bytecode. V0 refuses reference/pinned-reference literals because graph edges may not be hidden in metadata; references may already cross the ABI through receiver/argument/capture handles.

## Artifact chain

The first backend derives:

```text
lagrange-code/v0
      |
      v
wasm-module/v1
  content: validated WASM bytes
  metadata: ABI + literal pool + semantic calling shape
      |
      v
wasm-function/v1
  content: ref -> module
  metadata: ABI + entry + parameter count + capture binding IDs
      |
      v
Block
```

`CompilationService` registers `lagrange-code/v0 -> wasm-module/v1`. `compileWasmFunctionArtifact()` creates the corresponding function artifact. `wasm-function/v1` is registered with the normal `CodeExecutorRegistry`, so `ActivationExecutor` remains the execution entry point.

Both module and function artifacts are derived state under ADR 0007. Deleting them does not delete semantic code.

## Supported semantic subset

The first compiler supports:

- literal scalar Values
- positional arguments
- receiver
- captured bindings
- integer addition
- equality
- `if`

Message sends and nested Block creation are rejected explicitly. The executor never falls back silently to the interpreter when WASM compilation is requested.

The interpreter remains the reference implementation. Differential tests compile the same semantic artifact to `neutral-expression/v0` and WASM and require identical canonical results.

## Why handles first

A handle ABI is slower than immediately unboxing everything, but it keeps the architecture honest while the object model and Smalltalk seed are still evolving.

It permits refs, arbitrary integers, text and other tagged Values to cross the boundary without making WASM memory layout part of image semantics. Later optimized ABIs may specialize proven cases, for example unboxed integer paths or WASM-GC references, while retaining a generic handle path and the same `lagrange-code/v0` meaning.

## Security/capability consequence

A Value handle is not a capability. It only names a Value already admitted to the current activation. WASM code receives no ambient image/backend access from the handle arena.

Future imports for message sends, object access or Lagrange operations must still be explicitly provided and capability-checked at the runtime boundary.

## Deferred

- message-send host import
- nested closure creation from WASM
- mutable lexical cells/assignment
- WASM module grouping across multiple semantic Blocks
- module compilation/cache policy
- optimized/unboxed ABI variants
- WASM GC integration
- capability-aware host imports
- Lagrange placement and distributed execution policy
